# 새 Projectile 추가하기

## 문서 목적

이 문서는 Core 패키지의 Projectile 시스템 위에 **새로운 발사체 종류나 동작 정책**을 추가할 때,
어디를 먼저 보고 어떤 계층에 구현을 넣어야 하는지 정리한 레시피입니다.

현재 Core의 Projectile은 단순 이동 오브젝트가 아니라,
생성, 비주얼, 충돌, 타겟 추적, 종료 처리, 경계 처리까지 포함하는 전역 피드백 시스템에 가깝습니다.
따라서 새 Projectile은 프리팹 하나만 추가하는 방식보다,
**데이터 → 프리팹 → 컨트롤러 → 충돌/종료 규칙 → 호출부 연결** 순서로 설계하는 편이 안전합니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `Projectile/ProjectileController.cs`
- `Projectile/ProjectileBase.cs`
- `Projectile/ProjectileManager.cs`
- `Projectile/Visual/*`
- 관련 테이블 또는 설정 자산
- 호출부가 Skill 계열이라면 Skill 패키지의 `ProjectileEventDefinition`, `SkillExecutor`

---

## 언제 이 레시피를 사용하나요?

- 새로운 탄환/투사체 종류를 추가하고 싶을 때
- 기존 직선 투사체 외에 추적, 관통, 바운스, 체류형 투사체를 만들고 싶을 때
- Projectile 비주얼이나 충돌 정책을 확장하고 싶을 때

---

## 권장 구현 순서

## 1. 먼저 “투사체가 가진 규칙”을 분리해서 정의합니다

새 Projectile을 만들 때 가장 먼저 정해야 할 것은 프리팹이 아니라 규칙입니다.

예를 들어 다음을 먼저 정리합니다.

- 누가 생성하는가
- 어느 방향으로 발사되는가
- 충돌 대상은 누구인가
- 맞으면 즉시 종료되는가
- 관통하는가
- 벽/경계에 닿으면 어떻게 되는가
- 일정 시간 후 자동 종료되는가
- 비주얼은 본체와 분리되는가

이 규칙을 먼저 정리하지 않으면,
나중에 ProjectileBase가 지나치게 많은 if 분기를 가지게 됩니다.

---

## 2. 기존 ProjectileBase 확장인지, 새 정책 분리인지 판단합니다

새로운 동작을 추가할 때는 아래 기준으로 구분하는 것이 좋습니다.

- 기존 동작의 파라미터 변화면 데이터 추가
- 완전히 다른 이동/충돌 규칙이면 정책 분리 또는 새 파생 구현 고려

권장 방향은 다음과 같습니다.

- 이동 규칙은 controller/solver 성격으로 분리
- 충돌 후 처리 규칙은 hit/impact 정책으로 분리
- 비주얼은 visual 계층으로 분리

즉, ProjectileBase 한 곳에 모든 변형을 쌓지 않는 것이 중요합니다.

---

## 3. 데이터 공급원을 먼저 결정합니다

프로젝트 구조상 Projectile은 보통 테이블 또는 ScriptableObject 설정과 연결될 수 있습니다.

새 항목을 추가할 때는 다음을 먼저 정합니다.

- 이 투사체는 테이블 기반인가
- Addressables 프리팹 키가 필요한가
- 런타임에서 조회할 uid가 있는가
- 호출부가 어떤 식별자로 이 Projectile을 요청하는가

실무적으로는 **런타임 호출부가 프리팹 경로를 직접 모르게** 만드는 것이 중요합니다.

---

## 4. 프리팹은 “표현” 중심으로 유지합니다

Projectile 프리팹에는 다음 정도만 남기는 것이 좋습니다.

- 렌더러
- 충돌체
- 간단한 트레일/파티클
- ProjectileBase 또는 연결 컴포넌트

게임 규칙과 타격 처리 자체는 프리팹보다 런타임 컨트롤러 쪽에 두는 것이 유지보수에 좋습니다.
프리팹 안에 과도한 규칙을 넣으면, 나중에 Skill/Affect와 연결될 때 디버깅이 어려워집니다.

---

## 5. 생성 경로는 `ProjectileController` 기준으로 통일합니다

새 Projectile이 안정적으로 동작하려면,
생성 진입점이 `ProjectileController`나 그에 준하는 중앙 허브를 통하도록 유지하는 편이 좋습니다.

이유:
- 생성 위치 통일
- owner / source 정보 전달 통일
- 디버깅 경로 단순화
- 후처리 및 정리 정책 통일

특히 Skill 호출부가 직접 Instantiate를 하는 구조는 피하는 것이 좋습니다.

---

## 6. 충돌과 종료 규칙을 명확히 분리합니다

Projectile 기능 확장에서 가장 자주 문제가 나는 부분은 “맞았을 때 무엇을 하는가”와 “언제 제거되는가”입니다.

최소한 다음을 분리해서 보아야 합니다.

- hit 대상 수집
- 중복 hit 방지
- impact 시 데미지 / 상태 적용
- 관통 여부
- 종료 여부
- 비주얼 종료 연출

이 영역을 정리하지 않으면,
Projectile이 살아있는데 비주얼만 사라지거나,
이미 종료된 Projectile이 한 번 더 hit 하는 문제가 생기기 쉽습니다.

---

## 7. 경계 / 이동 / 추적은 독립 정책으로 본다

최근 구조상 바운더리, 이동 solver, 충돌 보정은 별도 확장 포인트로 보는 편이 좋습니다.

예를 들어,
- 직선 이동
- 홀드 후 발사
- 곡선 이동
- 대상 추적
- 바운스
- 월드 경계 충돌 처리

이런 기능을 모두 ProjectileBase에 누적하지 말고,
가능하면 별도 정책이나 helper로 분리하는 것이 좋습니다.

---

## 8. Skill/Affect와 연결될 때 소유권을 명확히 합니다

Projectile은 종종 Skill이나 Affect와 연결됩니다.
이때 책임은 다음처럼 나누는 것이 좋습니다.

- Skill/Affect: “무슨 Projectile을 쓸지” 결정
- Core Projectile: “Projectile을 어떻게 생성하고 이동시키는지” 처리
- hit 결과 적용: Damage / Affect 등 별도 시스템에 위임

Core Projectile이 Skill 세부 규칙까지 알게 되면 의존성이 쉽게 꼬입니다.

---

## 추천 구현 체크리스트

- 새 동작이 진짜 새 Projectile인지, 기존 파라미터 확장인지 구분했는가
- 런타임 식별자(uid/key)가 있는가
- 호출부가 프리팹 경로를 직접 알지 않는가
- 생성 경로가 `ProjectileController` 기준으로 통일되는가
- hit와 terminate 규칙이 명확한가
- 이동/추적/경계 정책이 분리 가능한가
- Skill/Affect 책임과 Core Projectile 책임이 섞이지 않는가

---

## 자주 생기는 문제

### 1. 생성은 되는데 정리가 안 됨

Projectile 수명 종료 시점을 명확히 두지 않아서 발생합니다.
timeout, hit, boundary, owner destroy 중 어떤 조건에서 종료되는지 먼저 고정해야 합니다.

### 2. 같은 대상에 여러 번 맞음

중복 hit 방지 키나 hit registry가 부족할 때 생깁니다.
관통형일수록 이 규칙이 중요합니다.

### 3. 시각 효과와 실제 충돌 위치가 다름

프리팹 pivot, collider offset, visual offset이 어긋난 경우가 많습니다.
디버그 Gizmo와 실제 판정을 함께 확인해야 합니다.

### 4. Skill 패키지에서 Projectile 세부 구현까지 참조함

하위/상위 계층 책임이 섞이면 확장이 어려워집니다.
Skill 쪽은 uid와 이벤트 정의만 알고, Core가 생성과 실행을 맡는 편이 좋습니다.

---

## 한 줄 정리

새 Projectile을 추가할 때는 **탄환 프리팹을 하나 더 만드는 작업**이 아니라,
**생성·이동·충돌·종료가 분리된 Projectile 규칙을 Core 안에 정식으로 추가하는 작업**으로 보는 것이 좋습니다.
