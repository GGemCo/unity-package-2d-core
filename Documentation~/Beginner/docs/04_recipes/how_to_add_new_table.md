# 새 테이블 추가하기

## 문서 목적

이 문서는 Core 패키지에 **새로운 txt 기반 테이블**을 추가할 때,
현재 프로젝트 구조에 맞춰 어떤 순서로 구현하고 연결해야 하는지 정리한 확장 레시피입니다.

Core는 테이블을 단순 텍스트 파일로만 다루지 않습니다.
런타임에서는 `TableLoaderManager`와 개별 `Table*` 로더를 통해 읽고,
게임 로딩 단계에서는 `GameLoaderManager`를 통해 초기화 순서에 맞게 준비합니다.
따라서 새 테이블을 추가할 때는 **파서 추가 → 매니저 노출 → 로딩 경로 확인 → 사용처 연결** 순서로 접근하는 것이 안전합니다.

---

## 언제 이 레시피를 사용하나요?

다음과 같은 경우에 적합합니다.

- 새로운 게임 데이터 종류를 txt 테이블로 관리하고 싶을 때
- 기존 `TableMonster`, `TableItem`, `TableWindow`와 비슷한 패턴의 데이터가 필요할 때
- 에디터에서 수정 가능하고, 런타임에서는 읽기 전용으로 쓰는 데이터가 필요할 때

반대로, 단일 프로젝트 설정처럼 개수가 적고 구조가 고정된 데이터라면 `ScriptableObject`가 더 적합할 수 있습니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `TableLoader/TableLoaderManager.cs`
- `TableLoader/Table/*`
- `Core/GameLoaderManager.cs`
- `Core/Loader/TableLoadStep.cs`
- `Configs/Addressables/ConfigAddressableTable.cs`
- 필요 시 Editor 쪽 `TableEditorWindow`, `TableRowEditorUtility`

---

## 권장 구현 순서

## 1. 테이블의 책임을 먼저 고정합니다

가장 먼저 아래를 정리합니다.

- 이 테이블이 무엇을 표현하는가
- 한 row의 key는 무엇인가
- 다른 테이블과 참조 관계가 있는가
- 런타임에서 자주 조회하는 기준은 무엇인가

예를 들어,
- 단일 key 조회가 많으면 `uid -> row` 캐시가 중요합니다.
- 1:N 조회가 많으면 `groupId -> List<row>` 보조 인덱스가 필요합니다.

이 단계에서 구조를 확정하지 않으면, 나중에 로더는 단순한데 사용처에서 매번 LINQ 검색을 하게 되어 런타임 비용과 유지보수 부담이 커집니다.

---

## 2. row 데이터 구조를 정의합니다

프로젝트의 기존 패턴에 맞춰, 한 줄 데이터를 담는 row 타입을 먼저 정의합니다.

일반적으로는 아래 역할이 필요합니다.

- 원본 txt 컬럼과 1:1로 대응되는 데이터 클래스
- key 역할을 하는 식별자 프로퍼티
- 문자열 → enum / number 변환 규칙

이 단계에서는 “편의 메서드가 많은 타입”보다 **로딩 결과를 담는 얇은 구조체/클래스**로 유지하는 것이 좋습니다.

권장 원칙:
- 파싱 책임은 row가 아니라 `Table*` 로더가 가진다
- row는 데이터 보관이 우선이다
- 런타임 규칙 해석은 다른 서비스나 resolver로 넘긴다

---

## 3. `Table*` 로더 클래스를 추가합니다

`TableLoader/Table/` 아래에 새 테이블 로더를 추가합니다.

이 클래스의 핵심 책임은 보통 다음과 같습니다.

- txt 파일 로드
- 줄 단위 파싱
- row 생성
- key 기준 캐시 구성
- 조회 API 제공

권장 메서드 예시는 다음과 같습니다.

- `Load(...)`
- `ParseRow(...)`
- `TryGet(...)`
- `GetAll()`
- 필요 시 `GetByGroup(...)`

중요한 점은, 이 클래스가 런타임의 **유일한 테이블 진입점**이 되도록 만드는 것입니다.
사용처가 txt 포맷이나 문자열 파싱 규칙을 직접 알게 하면 안 됩니다.

---

## 4. `TableLoaderManager`에 등록합니다

새 테이블이 실제로 사용되려면 `TableLoaderManager`에서 접근 가능해야 합니다.

이 단계에서 보통 다음 작업이 필요합니다.

- private 필드 추가
- 초기화 시점에 로더 생성 / 로드 연결
- public 프로퍼티 또는 getter 노출

권장 방향:
- 다른 시스템은 `TableLoaderManager`를 통해서만 접근한다
- 개별 테이블 로더를 직접 new 하거나 직접 파일 경로를 열지 않는다

이 패턴을 지키면 나중에 Addressables 경로가 바뀌거나, 로드 타이밍이 바뀌어도 영향 범위를 줄일 수 있습니다.

---

## 5. Addressables / 경로 상수를 연결합니다

현재 Core는 Addressables 기반 로딩 구조를 사용하므로,
테이블 파일도 키와 경로 규칙을 함께 정리해야 합니다.

확인 대상:
- `ConfigAddressableTable.cs`
- `ConfigAddressableKey.cs`
- `ConfigAddressablePath.cs`
- `AddressableLoaderSettings.cs` 또는 관련 로더

이 단계에서 중요한 점은 **문자열 하드코딩을 피하는 것**입니다.
새 테이블 키는 반드시 기존 Config 계층과 같은 방식으로 노출하는 편이 좋습니다.

---

## 6. 게임 로딩 흐름에서 보장되는지 확인합니다

새 테이블이 게임 시작 시 항상 필요하다면,
`GameLoaderManager`의 테이블 로딩 흐름에서 이 테이블이 준비된 상태가 보장되어야 합니다.

일반적으로는 `TableLoadStep` 이후 사용되는 구조가 이상적입니다.

체크 포인트:
- 이 테이블을 참조하는 시스템이 `Awake`에서 접근하는가
- 아니면 `Start` 이후 접근하는가
- 로딩 씬에서 선로드가 필요한가
- 런타임 중 동적 리로드가 필요한가

---

## 7. 사용처는 직접 row를 해석하지 않게 합니다

테이블을 연결한 후 실제 사용처에서는 다음 중 하나의 형태를 권장합니다.

- 전용 resolver
- 전용 service
- 전용 runtime definition builder

즉, `Table*`는 raw data를 제공하고,
실제 게임 규칙은 다른 계층이 해석하게 하는 것이 좋습니다.

예를 들어,
- 전투 규칙이면 `Definition` 또는 `Rule` 객체로 변환
- UI 표시 규칙이면 presenter용 DTO로 변환
- 저장 데이터라면 save/load용 키 체계로 변환

---

## 에디터까지 연결해야 하는 경우

새 테이블을 에디터에서 직접 수정하고 싶다면 다음도 함께 고려합니다.

- `TableEditorWindow`에서 노출할지
- `TableRowEditorUtility` 기반 편집을 지원할지
- 참조 컬럼 드롭다운이 필요한지
- 저장 시 전체 파일 재생성인지, row 단위 저장인지

실무적으로는 런타임 연결만 끝난 뒤, 에디터 지원은 두 번째 단계로 추가하는 편이 안전합니다.

---

## 추천 구현 체크리스트

- 테이블 책임이 한 문장으로 설명되는가
- key 조회 API가 있는가
- 필요한 보조 인덱스가 있는가
- `TableLoaderManager`에서 접근 가능한가
- Config / Addressables 경로가 상수화되어 있는가
- 게임 로딩 순서에서 안전한가
- 사용처가 txt 포맷을 직접 알지 않는가

---

## 자주 생기는 문제

### 1. 사용처가 row를 직접 가공함

이 경우 같은 해석 로직이 여러 곳에 중복됩니다.
해결 방법은 resolver나 definition 계층을 하나 두는 것입니다.

### 2. key 조회는 있는데 그룹 조회가 없음

초기에는 괜찮지만, 기능이 늘면 반복 검색이 늘어납니다.
자주 쓰는 조회 패턴은 로더 내부 인덱스로 올리는 편이 좋습니다.

### 3. Config 키와 실제 파일 경로가 어긋남

Addressables 기반 프로젝트에서 매우 자주 발생합니다.
경로 문자열을 코드 여러 곳에 흩뿌리지 말고 Config 계층 하나로 모으는 것이 좋습니다.

### 4. 로딩 전 접근

특히 `Awake`에서 테이블 접근하는 클래스가 있으면 초기화 순서 문제가 생길 수 있습니다.
이때는 `GameLoaderManager` 이후 사용이 보장되는지 먼저 확인해야 합니다.

---

## 한 줄 정리

새 테이블을 추가할 때는 **txt 포맷을 읽는 클래스**를 만드는 것이 아니라,
**Core의 로딩 구조 안에 들어가는 공식 데이터 진입점**을 만든다고 생각하는 것이 가장 안전합니다.
