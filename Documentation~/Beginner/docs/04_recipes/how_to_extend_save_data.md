# SaveData 확장하기

## 문서 목적

이 문서는 Core 패키지의 저장/복원 구조 위에 **새로운 저장 데이터 항목이나 저장 기여자**를 추가할 때,
현재 `SaveRegistry`와 `SaveDataManagerBase` 중심 구조에 맞춰 어떤 순서로 확장해야 하는지 정리한 레시피입니다.

현재 Core 저장 구조는 단순히 파일에 값을 적는 방식보다,
저장 기여자 등록, Envelope 구성, 로드 후 복원, 늦게 등록된 객체에 대한 restore 보정까지 포함하는 구조입니다.
따라서 새 저장 항목을 넣을 때는 **데이터 정의 → 기여자 작성 → 등록 시점 결정 → 복원 시점 검증 → 초기화 순서 점검** 순서가 가장 안전합니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `SaveData/Support/SaveRegistry.cs`
- `SaveData/Base/SaveDataManagerBase.cs`
- `SaveData/Support/ISaveContributor.cs`
- `SaveData/*`
- 관련 저장 데이터 컨테이너(`*Data.cs`)
- 실제 대상 클래스(예: Player, Inventory, Quest, UI 상태 등)

---

## 언제 이 레시피를 사용하나요?

- 플레이어의 새 상태값을 저장하고 싶을 때
- 시스템별 런타임 상태를 세이브 슬롯에 넣고 싶을 때
- 기존 로드/복원 흐름에 새로운 기여자를 추가하고 싶을 때

---

## 권장 구현 순서

## 1. 무엇을 저장할지 먼저 구분합니다

저장 대상은 크게 세 가지로 나누어 생각하는 것이 좋습니다.

- **영속 상태**: 다음 세션에도 반드시 유지되어야 하는 값
- **복원 가능한 파생 상태**: 원본 데이터로부터 다시 계산 가능한 값
- **일시 상태**: 저장하지 않아도 되는 값

가장 흔한 실수는 파생 상태까지 모두 저장하는 것입니다.
예를 들어 max 값에서 계산 가능한 값까지 함께 저장하면,
나중에 규칙이 바뀔 때 데이터 불일치가 발생하기 쉽습니다.

따라서 먼저 “이 값이 정말 저장 대상인가”를 판단하는 것이 중요합니다.

---

## 2. 저장 DTO를 명확히 정의합니다

새 저장 데이터는 런타임 객체를 그대로 직렬화하지 말고,
별도 데이터 컨테이너로 정의하는 것이 좋습니다.

권장 원칙:
- 저장용 타입은 순수 데이터 중심
- Unity 오브젝트 참조를 직접 넣지 않음
- 버전 변경에 대응하기 쉬운 형태 유지
- null / default 값 기준을 정함

이렇게 해야 저장 포맷을 나중에 점진적으로 확장하기 쉬워집니다.

---

## 3. 저장/복원 기여자를 만듭니다

Core 구조에서는 보통 개별 시스템이 `ISaveContributor` 같은 저장 기여자 역할을 합니다.

이 기여자의 핵심 책임은 다음과 같습니다.

- 현재 런타임 상태를 저장 DTO로 내보내기
- 저장 DTO를 다시 런타임 상태로 복원하기
- 저장 키 또는 등록 식별자를 안정적으로 제공하기

중요한 점은, 저장 매니저가 각 시스템 내부 상태를 직접 읽지 않도록 만드는 것입니다.
각 시스템이 **자기 상태를 자기 책임으로 저장/복원**하는 구조가 유지보수에 좋습니다.

---

## 4. 등록 시점을 신중하게 정합니다

저장 확장에서 가장 중요한 포인트 중 하나가 등록 시점입니다.

질문해야 할 항목:
- 이 객체는 언제 생성되는가
- 씬 전환 후 늦게 생성되는가
- 저장 로드보다 먼저 생성되는가
- 풀링 오브젝트인가

`SaveRegistry`를 쓰는 이유는 바로 이 초기화 순서 문제를 줄이기 위해서입니다.
따라서 새 기여자를 추가할 때는, “반드시 게임 시작 직후 존재한다”라고 가정하지 않는 편이 좋습니다.

---

## 5. 복원은 생성 직후 한 번에 끝난다고 가정하지 않습니다

현재 구조의 핵심은 늦게 등록되는 객체에도 restore를 다시 적용할 수 있다는 점입니다.
따라서 새 시스템을 확장할 때도 복원 코드는 아래 조건을 만족하는 것이 좋습니다.

- 여러 번 호출되어도 안전하다
- 아직 일부 참조가 준비되지 않았을 때 실패하지 않는다
- 가능한 범위만 먼저 적용하고, 나머지는 재적용 가능하다

즉, 복원 코드는 **idempotent**하고 **지연 초기화 친화적**이어야 합니다.

---

## 6. 저장과 표시를 분리합니다

저장 데이터 확장 시 자주 생기는 실수는,
복원 직후 UI를 직접 갱신하려고 하는 것입니다.

권장 방향:
- 저장 복원은 런타임 상태만 복구
- UI 갱신은 상태 변화 이벤트 또는 별도 sync 단계에서 수행

이렇게 해야 저장 시스템이 UI 구조와 강하게 결합되지 않습니다.

---

## 7. 즉시 저장이 필요한지, 지연 저장이 가능한지 판단합니다

새 저장 항목을 추가할 때는 저장 타이밍도 함께 정해야 합니다.

예를 들어,
- 전투 중 자주 바뀌는 값은 매 변경마다 저장하면 과도할 수 있음
- 장비 장착, 퀘스트 완료, 옵션 변경처럼 의미 있는 이벤트 시점만 저장해도 충분할 수 있음

`SaveDataManagerBase` 계층이 제공하는 저장 주기 정책과 맞추는 것이 좋습니다.

---

## 8. 호환성과 기본값을 함께 설계합니다

저장 포맷은 시간이 지나면 늘 확장됩니다.
따라서 새 필드를 추가할 때는 다음을 항상 생각해야 합니다.

- 기존 세이브에 이 값이 없으면 기본값은 무엇인가
- null 허용 여부는 어떤가
- 계산으로 복구 가능한가
- 버전 증가가 필요한가

이 관점을 놓치면 예전 세이브 로드 시 예외가 자주 발생합니다.

---

## 추천 구현 체크리스트

- 정말 저장해야 하는 값만 저장하는가
- 저장용 DTO가 순수 데이터 구조인가
- 기여자가 자기 상태를 자기 책임으로 저장/복원하는가
- `SaveRegistry` 등록 시점이 안전한가
- 복원 로직이 여러 번 호출돼도 안전한가
- UI 갱신이 저장 시스템과 분리되어 있는가
- 기본값 / 하위 호환 정책이 있는가

---

## 자주 생기는 문제

### 1. 저장은 되는데 복원이 누락됨

등록 시점이 늦거나, restore를 한 번만 한다고 가정할 때 자주 발생합니다.
`SaveRegistry` 지연 복원 패턴을 기준으로 다시 점검하는 것이 좋습니다.

### 2. 파생 값까지 저장해서 불일치 발생

나중에 계산 규칙이 바뀌면 기존 세이브와 충돌합니다.
원본 상태와 파생 상태를 구분해야 합니다.

### 3. 복원 중 null 참조 발생

다른 시스템이 아직 준비되지 않았는데 강하게 의존할 때 생깁니다.
복원은 가능한 범위만 적용하고, 필요 시 후속 sync 단계로 넘기는 편이 좋습니다.

### 4. UI가 저장 시스템에 직접 묶임

복원 후 UI까지 즉시 조작하면 구조가 금방 꼬입니다.
저장 복원은 상태 복구까지만 책임지는 것이 좋습니다.

---

## 한 줄 정리

SaveData를 확장할 때는 **값 하나를 더 저장하는 작업**이 아니라,
**초기화 순서와 지연 복원을 고려한 새로운 저장 기여자를 Core 저장 파이프라인에 등록하는 작업**으로 보는 것이 맞습니다.
