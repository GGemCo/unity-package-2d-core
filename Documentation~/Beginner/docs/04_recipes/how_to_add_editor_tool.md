# 새 Editor Tool 추가하기

## 문서 목적

이 문서는 Core 패키지의 Editor 영역에 **새로운 테스트 툴, 편집 창, 생성 도구**를 추가할 때,
현재 `GGemCoTool`, `GGemCoProjectSetup`, `GGemCoCreator` 축에 맞춰 어떤 방식으로 설계하면 좋은지 정리한 레시피입니다.

Core Editor는 단순한 유틸 스크립트 모음이 아니라,
테이블 편집기, 테스트 창, 셋업 스텝, 생성 허브가 역할별로 나뉜 구조를 가지고 있습니다.
따라서 새 툴을 추가할 때는 **도구 성격 구분 → Runtime 의존 범위 확인 → 창/서비스 분리 → 저장/Undo/검증 연결** 순서로 접근하는 것이 좋습니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `GGemCoTool/*`
- `GGemCoProjectSetup/*`
- `GGemCoCreator/*`
- 공통 유틸: `TableRowEditorUtility`, `SearchableDropdownUtility`
- 관련 Runtime 클래스 및 asmdef 구성

---

## 언제 이 레시피를 사용하나요?

- 테스트용 EditorWindow를 추가하고 싶을 때
- 테이블 기반 데이터 편집기를 만들고 싶을 때
- 프로젝트 셋업 자동화 스텝을 추가하고 싶을 때
- 특정 리소스 생성기(factory)를 허브에 연결하고 싶을 때

---

## 1. 먼저 도구의 종류를 구분합니다

새 Editor Tool은 보통 아래 넷 중 하나에 속합니다.

- **테스트 도구**: Play Mode에서 런타임 검증
- **편집 도구**: 데이터/에셋 수정
- **셋업 도구**: 프로젝트 초기 설정 자동화
- **생성 도구**: 신규 에셋/프리팹 생성

이 분류를 먼저 정하면,
파일 위치와 의존 범위를 훨씬 쉽게 결정할 수 있습니다.

예를 들어,
- Play Mode 대상 테스트 창이면 `GGemCoTool/Test` 계열
- 테이블 편집 확장이면 `GGemCoTool/TableEditor` 계열
- 프로젝트 자동 설정이면 `GGemCoProjectSetup`
- 새 에셋 생성기면 `GGemCoCreator`

---

## 2. Runtime 의존을 명확히 제한합니다

Editor Tool은 Runtime을 참조할 수 있지만,
Runtime이 Editor를 참조하게 만들면 안 됩니다.

새 툴을 추가할 때는 다음을 점검합니다.

- Runtime 타입을 읽기만 하는가
- Editor 전용 보조 타입이 Runtime 쪽에 섞이지 않는가
- 테스트 도구가 실제 게임 코드와 강하게 결합되지 않는가

특히 임시 디버그 편의 코드를 Runtime에 넣고 Editor에서 호출하는 방식은,
짧게는 편하지만 장기적으로 구조를 망가뜨리기 쉽습니다.

---

## 3. 창 자체와 로직을 분리합니다

새 EditorWindow를 만들 때는 창 클래스 하나에 모든 로직을 몰아넣지 않는 것이 좋습니다.

권장 분리:
- EditorWindow: 레이아웃, 탭, 상태 표시
- Service/Module: 실제 처리 로직
- Utility: 공통 위젯, 드롭다운, reflection 편집, 검증

이 패턴은 특히 창이 커질수록 중요합니다.
처음부터 완벽히 나눌 필요는 없지만,
최소한 “UI 그리기”와 “실제 파일 수정/테스트 실행”은 나누는 편이 좋습니다.

---

## 4. 공통 UI 유틸을 적극 재사용합니다

Core Editor에는 이미 재사용 가치가 높은 유틸이 있습니다.

예:
- `SearchableDropdownUtility`
- `TableRowEditorUtility`
- 테이블 reflection/validation 계열

새 툴에서 또 다른 드롭다운이나 행 편집기를 새로 만드는 것보다,
기존 유틸 위에 얹는 편이 일관성과 유지보수성 모두에서 좋습니다.

---

## 5. 수정 도구라면 Undo와 Dirty 처리를 함께 설계합니다

에디터 도구에서 실제 자산을 수정한다면,
아래 두 가지를 반드시 함께 생각해야 합니다.

- Undo 가능한가
- 변경 사항이 저장 대상으로 표시되는가

실무적으로는 “동작은 했는데 저장이 안 됨”, “Undo가 안 돼서 데이터가 망가짐” 문제가 매우 자주 발생합니다.
따라서 수정 계열 툴은 기능 구현과 동시에 Undo/Dirty 설계를 같이 해야 합니다.

---

## 6. Play Mode 테스트 툴은 런타임 객체 수명주기를 존중합니다

테스트 툴이 Play Mode에서 캐릭터, VFX, Projectile 등을 다룬다면,
다음 규칙을 먼저 지키는 편이 좋습니다.

- 직접 static 상태를 오염시키지 않는다
- 테스트 대상 생성/삭제 경로를 명확히 한다
- 종료 시 정리한다
- 씬이 바뀌어도 실패하지 않는가를 확인한다

즉, 테스트 도구는 편의 기능이지만,
실제 런타임 생명주기를 무시하면 디버깅을 더 어렵게 만들 수 있습니다.

---

## 7. 메뉴 경로와 접근 지점을 통일합니다

새 도구는 어디서 찾을 수 있는지가 중요합니다.

권장 방향:
- 패키지별 메뉴 경로를 통일
- 테스트/설정/생성 계열을 섞지 않음
- 이름만 보고 역할이 드러나게 작성

도구 수가 늘수록 메뉴 정리가 곧 생산성입니다.

---

## 8. 작은 도구라도 문서화와 사용 범위를 남깁니다

새 Editor Tool은 나중에 만든 사람만 쓰는 경우가 많습니다.
이를 방지하려면 최소한 아래를 남기는 것이 좋습니다.

- 이 툴이 무엇을 위한 것인지
- Play Mode가 필요한지
- 어떤 자산/씬을 전제로 하는지
- 수정이 실제 파일에 반영되는지

간단한 README 또는 창 상단 설명만 있어도 온보딩 효율이 크게 올라갑니다.

---

## 추천 구현 체크리스트

- 테스트/편집/셋업/생성 중 어떤 도구인지 명확한가
- Runtime → Editor 역참조가 생기지 않는가
- 창과 로직이 적절히 분리되어 있는가
- 공통 유틸을 재사용하는가
- 수정 도구라면 Undo/Dirty 처리가 있는가
- Play Mode 테스트라면 생성/정리가 명확한가
- 메뉴 경로가 일관적인가
- 사용 범위와 전제 조건이 문서화되어 있는가

---

## 자주 생기는 문제

### 1. 창 클래스가 너무 커짐

초기에는 빠르지만, 유지보수가 급격히 어려워집니다.
탭/패널/서비스 단위로 조금씩 분리하는 것이 좋습니다.

### 2. Runtime에 Editor 편의 코드가 섞임

테스트는 쉬워지지만 패키지 경계가 무너집니다.
Editor 전용 코드는 Editor 어셈블리에 남기는 편이 좋습니다.

### 3. 자산 수정은 되는데 Undo가 안 됨

실무에서 가장 위험한 문제 중 하나입니다.
특히 테이블/ScriptableObject 수정 툴은 Undo를 먼저 고려하는 것이 좋습니다.

### 4. Play Mode 의존 툴이 씬 조건을 강하게 가정함

특정 씬에서만 동작하는데 안내가 없으면 사용성이 급격히 떨어집니다.
툴 안에 전제 조건을 표시하는 것이 좋습니다.

---

## 한 줄 정리

새 Editor Tool을 추가할 때는 **편한 창 하나를 더 만드는 작업**이 아니라,
**Core Editor 워크플로우 안에 들어가는 테스트/편집/셋업/생성 도구를 역할에 맞게 추가하는 작업**으로 보는 것이 좋습니다.
