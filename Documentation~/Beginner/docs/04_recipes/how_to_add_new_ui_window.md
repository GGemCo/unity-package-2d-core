# 새 UI 윈도우 추가하기

## 문서 목적

이 문서는 Core 패키지에 **새로운 UGUI 기반 UI 윈도우**를 추가할 때,
현재 프로젝트의 `UIWindowManager` 중심 구조에 맞춰 어떤 순서로 설계하고 연결하면 좋은지 정리한 레시피입니다.

Core의 UI는 단순히 프리팹을 열고 닫는 구조가 아니라,
윈도우 공통 베이스, 매니저, 아이콘/슬롯, Presenter/Controller 연결 흐름을 함께 가집니다.
따라서 새 창을 추가할 때는 **프리팹 제작 → 윈도우 클래스 추가 → 매니저 등록 → 데이터 연결 → 초기화 순서 검증** 방식으로 접근하는 것이 좋습니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `UI/Core/Base/UIWindowManager.cs`
- `UI/Core/Base/UIWindow.cs`
- `UI/Core/Base/UIWindowBase.cs`
- 관련 `UIElement*`, `UIIcon*`, `Presenter` 계열
- 플레이어 상태와 연결된다면 `Characters/Player/PlayerUIController.cs`
- 테이블 기반 UI라면 `TableLoader/`

---

## 언제 이 레시피를 사용하나요?

- 인벤토리, 정보창, 설정창, 퀘스트창 같은 새 창을 만들고 싶을 때
- 기존 HUD와 별개로 열고 닫는 독립 윈도우가 필요할 때
- 드래그 앤 드롭, 슬롯, 아이콘 구조를 재사용하고 싶을 때

반대로, 캐릭터 머리 위 체력바처럼 월드 공간에 붙는 UI는 일반 윈도우보다 Presenter/개별 View 구조가 더 적합할 수 있습니다.

---

## 권장 구현 순서

## 1. 이 창이 “윈도우”인지 먼저 판단합니다

새 UI가 아래 특징을 가지면 `UIWindow` 계열로 가는 것이 적합합니다.

- 열기 / 닫기 상태가 있다
- 공용 Canvas 아래에서 관리된다
- 다른 창과 함께 정렬 / 포커스 / 표시 상태를 맞춰야 한다
- 슬롯 / 아이콘 / 스크롤 리스트를 포함한다

반대로,
- 항상 떠 있는 HUD
- 캐릭터 추적형 UI
- 일회성 효과성 UI
라면 일반 윈도우보다 별도 presenter 구조가 더 적합할 수 있습니다.

---

## 2. 프리팹의 책임을 최소화합니다

프리팹은 다음 역할만 가지는 것이 좋습니다.

- 레이아웃
- 기본 UI 참조 연결
- 애니메이션 / 표시 구조

데이터 계산이나 게임 규칙은 프리팹 안에서 하지 않습니다.
예를 들어, “현재 플레이어의 어떤 상태를 어떤 순서로 보여줄지”는
윈도우 클래스나 presenter가 담당하는 것이 좋습니다.

---

## 3. 새 윈도우 클래스를 추가합니다

보통 아래 중 하나를 기준으로 시작합니다.

- `UIWindow` 상속
- 프로젝트 공통 윈도우 베이스가 있다면 그 베이스 상속

이 클래스의 핵심 책임은 다음 정도가 적절합니다.

- 참조 캐싱
- open / close 시점 처리
- 바인딩 / 언바인딩
- child element 초기화
- presenter나 외부 controller와 연결

권장 원칙:
- 데이터 계산은 최소화
- 외부 이벤트 구독은 `OnOpen`/`OnClose` 또는 명확한 bind/unbind 지점에서 관리
- child `UIElement*`는 재사용 가능한 단위로 분리

---

## 4. 필요한 `UIElement*`를 분리합니다

창 안에 반복적으로 쓰이는 블록이 있다면,
윈도우 하나에 모든 갱신 로직을 몰지 말고 `UIElement*`로 분리하는 것이 좋습니다.

예를 들어,
- 리스트 row
- 아이콘 셀
- 버프 슬롯
- 장비 슬롯
- 탭 버튼

이렇게 나누면 다음 장점이 있습니다.

- 프리팹 재사용 가능
- 테스트 범위 축소
- 아이콘/슬롯 교체가 쉬움
- drag & drop 연결이 자연스러움

---

## 5. `UIWindowManager` 등록 방식을 맞춥니다

새 창이 실제로 열리려면 `UIWindowManager`가 이 창의 존재를 알아야 합니다.

프로젝트 구조에 따라 다르지만 일반적으로는 다음을 점검합니다.

- 창 프리팹이 어디서 로딩되는가
- 시작 시 미리 준비되는가, 필요 시 로드되는가
- 창 식별 키가 있는가
- 다른 시스템이 어떤 API로 열고 닫는가

중요한 점은, 게임 로직이 직접 프리팹 instantiate를 하지 않고,
가능하면 `UIWindowManager`를 통해 창 생명주기를 통일하는 것입니다.

---

## 6. 데이터 공급자는 윈도우 밖에 둡니다

UI 창 자체가 플레이어 상태, 저장 데이터, 테이블, 아이템 규칙을 모두 아는 구조는 금방 비대해집니다.

권장 구조:
- 상태 계산: Controller / Presenter
- 표시 갱신: UIWindow
- 반복 cell 렌더링: UIElement

예를 들어 플레이어 자원 UI 계열은 `PlayerUIController`가 외부 상태를 묶고,
각 실제 윈도우나 element가 렌더링만 담당하는 방향이 유지보수에 좋습니다.

---

## 7. open / close 시점의 구독 정리를 명확히 합니다

새 창에서 가장 흔한 문제는 이벤트 중복 구독입니다.

권장 규칙:
- 열릴 때 구독, 닫힐 때 해제
- 또는 `Bind(target)` / `Unbind()`를 명시적으로 제공
- 풀링되는 UI라면 `OnEnable/OnDisable`만 믿지 말고, 매니저 생명주기에 맞춘다

특히 플레이어 생성/파괴가 반복되는 씬에서는,
기존 플레이어 이벤트를 해제하지 않으면 null 참조나 중복 갱신 문제가 생기기 쉽습니다.

---

## 8. HUD와 팝업, 윈도우를 섞지 않습니다

Core에는 `PopupManager`, `SystemMessageManager`, HUD 계열 UI, 일반 윈도우가 각각 따로 존재합니다.
새 UI를 추가할 때 이 역할을 구분해야 합니다.

- 확인/경고성 단발 UI → Popup
- 짧은 정보 출력 → SystemMessage
- 항상 떠 있는 자원 표시 → HUD
- 열고 닫는 패널형 UI → UIWindow

이 구분이 흐려지면 UI 구조 전체가 금방 복잡해집니다.

---

## 추천 구현 체크리스트

- 이 UI가 정말 윈도우인가
- 프리팹은 레이아웃 중심인가
- 데이터 계산이 윈도우 안에 과도하게 들어가지 않았는가
- 반복 블록이 `UIElement*`로 분리되어 있는가
- `UIWindowManager`를 통한 생명주기 관리가 가능한가
- 이벤트 구독/해제가 명확한가
- 팝업/HUD/SystemMessage와 역할이 섞이지 않는가

---

## 자주 생기는 문제

### 1. 창 클래스가 게임 규칙까지 계산함

UI는 빨리 붙지만, 수정이 매우 어려워집니다.
계산 로직은 Presenter/Controller로 빼는 것이 좋습니다.

### 2. open할 때마다 중복 구독됨

특히 플레이어 상태 UI에서 자주 생깁니다.
반드시 bind/unbind 지점을 명확히 두는 편이 좋습니다.

### 3. 리스트 렌더링을 매 프레임 전체 재생성함

성능과 GC 모두에 불리합니다.
가능하면 diff 갱신, 풀링, presenter 집계를 고려해야 합니다.

### 4. 프리팹 로딩 경로와 매니저 등록 방식이 분리됨

창 자체는 만들어졌는데 매니저가 못 찾는 상황이 생깁니다.
키/로딩 경로/초기화 위치를 함께 점검해야 합니다.

---

## 한 줄 정리

새 UI 윈도우를 추가할 때는 **화면 하나를 만드는 작업**이 아니라,
**`UIWindowManager`와 Presenter 구조 안에 들어가는 새로운 표시 계층을 추가하는 작업**으로 보는 것이 좋습니다.
