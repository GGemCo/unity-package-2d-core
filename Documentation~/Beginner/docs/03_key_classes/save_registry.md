# SaveRegistry

## 1. 문서 목적

이 문서는 `SaveRegistry`를 설명합니다.
저장 기여자 등록과 복원 시점 연결을 어떻게 관리하는지, 그리고 초기화 순서 문제를 어떻게 줄이는지 이해하는 것이 목적입니다.

---

## 2. 역할

`SaveRegistry`는 **저장 기여자 중앙 레지스트리**입니다.
`ISaveContributor`를 등록해 두고, 저장 시에는 모든 기여자로부터 데이터를 수집하고, 복원 시에는 모든 기여자에게 데이터를 다시 배포하는 구조를 돕습니다.

가장 중요한 특징은 **지연 복원(late restore)** 입니다.
이미 로드된 `SaveEnvelope`가 있는데 기여자가 나중에 등록되더라도, 그 기여자에게 즉시 `Restore()`를 적용할 수 있습니다.

---

## 3. 왜 중요한가

저장/복원 시스템의 가장 흔한 문제는 초기화 순서입니다.

- 로드는 끝났는데 어떤 객체는 아직 생성되지 않았다
- 새로 생성된 UI/플레이어가 저장 상태를 받아야 한다
- 씬 전환 후 늦게 등록된 객체가 이전 상태를 모르고 시작한다

`SaveRegistry`는 이런 문제를 완화하기 위한 핵심 장치입니다.
단순 리스트 저장소가 아니라 “현재 복원해야 할 Envelope를 기억하는 레지스트리”라는 점이 중요합니다.

---

## 4. 핵심 상태

### 기여자 목록
- `List`

등록된 `ISaveContributor` 목록입니다.
우선순위에 따라 정렬됩니다.

### 지연 복원 상태
- `_pendingRestore`

이미 로드된 저장 데이터를 보관하고 있다가, 나중에 등록되는 기여자에게도 즉시 적용합니다.

### 등록 이벤트
- `Registered`

기여자 등록 자체를 다른 시스템이 감지할 수 있게 해 줍니다.

---

## 5. 주요 메서드

### `EnsureInitialized()`
런타임 시작 전에 레지스트리를 초기화합니다.
정적 상태가 씬 간에 남는 문제를 줄이는 데 중요합니다.

### `Register(ISaveContributor contributor)`
기여자 등록 진입점입니다.

이 메서드는 다음을 수행합니다.

1. null/중복 등록 방지
2. 목록 추가
3. `Priority` 기준 정렬
4. 등록 이벤트 발행
5. `_pendingRestore`가 있으면 즉시 `Restore()` 적용

즉, 등록과 복원을 분리하지 않고 연결해 둔 구조입니다.

### `ApplyRestore(SaveEnvelope env)`
로드 직후 `SaveDataManager`가 호출하는 대표 메서드입니다.

이 메서드는
- 현재 등록된 기여자에게 즉시 `Restore()`를 호출하고
- 이후 등록될 기여자를 위해 `_pendingRestore`를 기억합니다.

### `Unregister(ISaveContributor contributor)`
기여자를 목록에서 제거합니다.
풀링 해제, 파괴, 씬 종료 시점에 중요합니다.

### `ClearPendingRestore()`
새 게임 시작처럼 이전 로드 상태를 버려야 할 때 사용합니다.

### `Clear()`
전체 목록과 보류 복원 상태, 이벤트를 모두 정리합니다.
테스트/씬 초기화/강제 리셋에 유용합니다.

## 6. 연결해서 봐야 하는 클래스

### 계약과 데이터
- `ISaveContributor`
- `SaveEnvelope`

### 저장 매니저
- `SaveDataManagerBase`
- `SaveDataLoader`

### 실제 기여자
- 플레이어 데이터 기여자
- UI 상태 기여자
- 패시브/아이템/퀘스트 등 상태 저장 객체

---

## 7. 대표 런타임 흐름

### 흐름 A: 일반 저장
1. 여러 시스템이 `ISaveContributor`로 등록되어 있습니다.
2. 저장 매니저가 `BuildEnvelopeForSave()`를 호출합니다.
3. 각 기여자가 `Capture(env)`로 데이터를 기록합니다.

### 흐름 B: 로드 직후 복원
1. 저장 파일에서 `SaveEnvelope`를 읽습니다.
2. `ApplyRestore(env)`를 호출합니다.
3. 현재 등록된 모든 기여자에게 즉시 `Restore(env)`가 적용됩니다.
4. `_pendingRestore`에 env가 남습니다.

### 흐름 C: 늦게 생성된 객체 복원
1. 플레이어나 UI가 로드 후 늦게 생성됩니다.
2. 해당 객체가 `Register()`를 호출합니다.
3. `SaveRegistry`가 `_pendingRestore`를 보고 즉시 `Restore()`를 호출합니다.

---

## 8. 확장 포인트

### 새 시스템을 저장 대상에 포함할 때
별도 저장 매니저 분기를 늘리기보다, `ISaveContributor`를 구현해서 등록하는 방향이 맞습니다.

### 복원 순서를 제어할 때
`Priority`를 활용해 저장 기여자 간 순서를 명시하는 편이 좋습니다.
암묵적 Awake/Start 순서에 기대는 구조는 피하는 것이 좋습니다.

---

## 9. 디버깅 체크리스트

### 로드했는데 어떤 객체만 상태가 초기값인 경우
- 그 객체가 `Register()`를 호출했는지 확인합니다.
- 등록이 너무 늦어도 `_pendingRestore` 덕분에 복원되어야 하므로, 등록 자체 누락 여부를 먼저 봅니다.

### 같은 상태가 두 번 복원되는 경우
- 중복 등록이 있는지 확인합니다.
- 파괴 후 재생성된 객체가 이전 등록을 해제하지 않았는지 확인합니다.

### 새 게임 시작인데 이전 상태가 남는 경우
- `ClearPendingRestore()` 호출 여부를 확인합니다.
- 필요 시 `Clear()`가 더 적절한 상황인지 검토합니다.

---

## 10. 한 줄 정리

`SaveRegistry`는 **저장 기여자를 중앙에서 관리하고, 이미 로드된 저장 데이터를 늦게 등록된 객체에도 자동 복원해 주는 Core 저장/복원 연결 장치**입니다.
