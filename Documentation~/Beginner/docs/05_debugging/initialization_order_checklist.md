# 초기화 순서 점검 체크리스트

## 문서 목적

이 문서는 Core 패키지에서 **로딩, 씬 전환, 런타임 오브젝트 생성 시점, 지연 등록**이 얽힐 때
어떤 순서로 문제를 추적해야 하는지 정리한 디버깅 체크리스트입니다.

Core는 단일 클래스 하나가 모든 초기화를 끝내는 구조가 아니라,
`GameLoaderManager`, `SceneGame`, `TableLoaderManager`, Addressables 로더, 저장/복원 기여자, UI 매니저, 캐릭터 생성 흐름이 이어지며
여러 시스템이 서로 다른 타이밍에 준비됩니다.
그래서 “null 이 떴다”, “값이 적용되지 않았다”, “UI가 비었다” 같은 증상은
실제로는 **초기화 순서 문제**일 가능성이 매우 높습니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `Core/GameLoaderManager.cs`
- `Scenes/SceneGame.cs`
- `TableLoader/TableLoaderManager.cs`
- `AddressableLoader/*`
- `SaveData/Support/SaveRegistry.cs`
- `UI/Core/Base/UIWindowManager.cs`
- 각 패키지별 `Bootstrapper*`, `PackageManager*`

---

## 이런 증상에서 먼저 봅니다

- 게임 시작 직후 특정 참조가 null 이다
- 테이블 값은 있는데 실제 런타임에는 적용되지 않는다
- 저장 데이터는 로드됐는데 캐릭터나 UI에 반영되지 않는다
- 씬을 다시 열면 어떤 시스템만 늦게 붙는다
- 플레이어 생성 직후 입력, UI, 카메라, 패키지 브리지가 일부만 연결된다

---

## 점검 순서

## 1. 문제를 “어느 단계에서” 처음 관측했는지 분리합니다

먼저 다음 중 어느 구간인지부터 분류합니다.

- 앱 시작 직후
- 로딩 씬 진행 중
- 게임 씬 진입 직후
- 캐릭터 생성 직후
- 저장 복원 직후
- 씬 재진입 또는 재스폰 직후

초기화 순서 문제는 원인이 한참 앞 단계에 있는 경우가 많습니다.
따라서 오류가 터진 지점만 보지 말고, **처음 전제가 무너진 지점**을 찾아야 합니다.

---

## 2. 필수 선행 데이터가 준비되었는지 확인합니다

대부분의 Runtime 시스템은 다음 세 축 중 하나를 선행 조건으로 가집니다.

- 테이블 데이터
- ScriptableObject 설정
- Addressables 리소스 또는 프리팹

따라서 어떤 시스템이 실패했다면,
그 시스템이 요구하는 선행 데이터가 정말 준비되었는지를 먼저 확인합니다.

질문 예시:
- 관련 테이블이 이미 로드되었는가
- 관련 Settings SO가 로드되었는가
- 필요한 프리팹/윈도우/VFX가 Addressables로 준비되었는가

---

## 3. 생성 순서와 바인딩 순서를 분리해서 봅니다

초기화 문제에서 자주 놓치는 부분은 “오브젝트가 존재한다”와 “연결이 끝났다”를 같은 의미로 보는 것입니다.

예를 들어:
- Player 오브젝트는 이미 존재하지만
- PlayerUIController 구독은 아직 안 붙었을 수 있고
- UIWindowManager는 창을 만들었지만
- HUD Presenter는 아직 대상 캐릭터를 못 찾았을 수 있습니다

즉, **생성 완료**와 **바인딩 완료**는 따로 확인해야 합니다.

---

## 4. Awake / OnEnable / Start / 로더 완료 시점을 섞어서 추적하지 않습니다

Unity에서는 같은 초기화라도 어떤 클래스는 `Awake`, 어떤 클래스는 `Start`, 어떤 클래스는 Addressables 완료 콜백,
어떤 클래스는 씬 매니저나 로딩 매니저의 후속 단계에서 동작합니다.

따라서 디버깅할 때는 로그를 다음처럼 그룹화하는 것이 좋습니다.

- 오브젝트 생성 시점
- 필수 데이터 로드 완료 시점
- 구독/등록 시점
- 첫 sync 시점
- 첫 사용자 입력 또는 첫 Tick 시점

이렇게 나누면 “누가 더 늦었는지”가 훨씬 잘 보입니다.

---

## 5. 저장 복원은 별도 축으로 분리해서 봅니다

저장 복원은 초기화와 겹치지만, 완전히 같은 문제는 아닙니다.

자주 생기는 오해:
- 로드는 성공했는데 적용이 안 됨
- 사실 로드 실패가 아니라 복원 대상이 아직 등록되지 않음
- 또는 복원은 됐는데 UI sync 가 늦음

따라서 저장 이슈가 의심되면 반드시 다음을 따로 봅니다.

- 저장 데이터가 메모리로 들어왔는가
- 복원 기여자가 등록되었는가
- 복원 호출이 실제로 갔는가
- 복원 후 상태 변경 이벤트가 발행되었는가

---

## 6. 씬 단위 싱글톤과 패키지 매니저 중복 여부를 확인합니다

초기화 순서 문제처럼 보여도,
실제로는 패키지 매니저나 싱글톤이 중복 생성되어 발생하는 경우가 있습니다.

체크 항목:
- 같은 매니저가 씬마다 중복 존재하는가
- DontDestroyOnLoad 객체가 다시 생성되는가
- 이전 씬 구독이 해제되지 않았는가
- 인스턴스가 교체되었는데 참조는 이전 것을 들고 있는가

이 경우는 순서 문제가 아니라 **인스턴스 생명주기 문제**입니다.

---

## 7. 지연 생성 객체를 강한 전제로 취급하지 않습니다

UI, 플레이어, 몬스터, 드롭 오브젝트, 저장 기여자, 이펙트 루트처럼
런타임 중 늦게 생기는 객체는 “게임 시작 시 이미 존재한다”라고 가정하면 쉽게 깨집니다.

권장 기준:
- 한 번에 다 준비된다고 가정하지 않기
- 등록 후 즉시 재동기화 가능한 구조 유지
- null 이면 다음 프레임에 재시도할지, 이벤트 기반으로 기다릴지 결정하기

---

## 빠른 체크리스트

- 문제를 처음 관측한 단계가 명확한가
- 관련 테이블 / Settings / Addressables 가 먼저 준비되었는가
- 오브젝트 생성과 바인딩 완료를 구분해서 확인했는가
- Awake / Start / 로더 완료 / 첫 Tick 을 분리해서 로그를 봤는가
- 저장 로드와 저장 복원을 구분해서 확인했는가
- 패키지 매니저 / 싱글톤 중복 생성 가능성을 확인했는가
- 지연 생성 객체를 즉시 존재한다고 가정하고 있지 않은가

---

## 자주 생기는 문제

### 1. 씬 진입 직후 UI가 비어 있음

대부분 UI 생성은 끝났지만,
대상 플레이어나 데이터 구독이 아직 붙지 않은 경우입니다.
UIWindow 생성과 Presenter 바인딩 시점을 분리해서 확인하는 것이 좋습니다.

### 2. 저장값이 첫 프레임에는 기본값처럼 보임

로드는 끝났지만 복원이 늦게 적용되거나,
복원 후 UI sync 가 다음 단계에서 이루어지는 경우가 많습니다.

### 3. 특정 참조만 가끔 null 이 됨

고정 순서가 아니라 이벤트 기반/비동기 로드 기반이면
환경에 따라 순서가 달라질 수 있습니다.
이럴 때는 재현 빈도보다 선행 조건을 먼저 확인해야 합니다.

### 4. 플레이 모드 재시작 때만 이상함

정적 캐시, 싱글톤 잔존, Domain Reload 옵션, 에디터 전용 부트스트랩이 영향을 줄 수 있습니다.
런타임 초기화와 에디터 재생성 흐름을 구분해서 보는 것이 좋습니다.

---

## 한 줄 정리

초기화 순서 문제는 “누가 null 인가”보다 **무엇이 아직 준비되지 않았는데 준비되었다고 가정했는가**를 찾는 방식으로 추적하는 것이 가장 빠릅니다.
