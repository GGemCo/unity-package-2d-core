# 저장 / 복원 점검 체크리스트

## 문서 목적

이 문서는 Core 패키지에서 **세이브는 되는데 로드가 안 되거나, 로드는 되는데 실제 상태가 맞지 않거나,
일부 시스템만 복원되지 않는 문제**를 추적할 때 사용할 체크리스트입니다.

Core의 저장 구조는 단순 파일 입출력보다,
`SaveDataManagerBase`의 저장 파이프라인과 `SaveRegistry`의 등록/지연 복원 구조를 통해
여러 시스템이 자기 상태를 저장하고 다시 복원하는 방식에 가깝습니다.
따라서 저장 버그는 파일 자체보다 **기여자 등록, 복원 시점, 재동기화 책임**에서 자주 발생합니다.

---

## 먼저 확인할 관련 클래스 / 폴더

- `SaveData/Base/SaveDataManagerBase.cs`
- `SaveData/Support/SaveRegistry.cs`
- `SaveData/Support/ISaveContributor.cs`
- 각 시스템별 `*Data.cs`, `*SaveData*`
- 저장 이후 UI 또는 Presenter 연결 지점

---

## 이런 증상에서 먼저 봅니다

- 저장 후 재시작하면 값이 초기화된다
- 일부 값만 저장되고 일부 값은 빠진다
- 로드는 되었는데 실제 캐릭터 / UI에 반영되지 않는다
- 씬 재진입 직후만 값이 이상하다
- 늦게 생성되는 오브젝트만 복원이 누락된다
- 예전 세이브를 읽으면 일부 필드가 깨진다

---

## 점검 순서

## 1. 문제를 저장 단계와 복원 단계로 나눕니다

저장/로드 문제는 먼저 다음 둘 중 어디인지 분리해야 합니다.

- 저장 파일에 값이 아예 안 들어갔다
- 파일에는 있는데 런타임 복원이 안 됐다

이 구분 없이 바로 복원 코드를 보면 시간을 많이 낭비하게 됩니다.

먼저 확인할 질문:
- 직렬화된 결과에 값이 실제로 기록되었는가
- 기록된 값을 로드 시 다시 읽어왔는가

---

## 2. 어떤 시스템이 저장 기여자인지 확인합니다

Core 구조에서는 보통 각 시스템이 자기 상태를 직접 내보내고 복원합니다.
따라서 문제를 추적할 때는 “저장 매니저가 왜 안 했지?”보다
**어느 기여자가 이 데이터를 책임지는가**를 먼저 확인해야 합니다.

체크 항목:
- 해당 값을 누가 수집하는가
- 저장 DTO 는 어디에 들어가는가
- 복원은 누가 처리하는가
- 등록 식별자나 키가 안정적인가

---

## 3. 등록 시점이 늦은 객체인지 확인합니다

복원 누락 문제에서 가장 흔한 원인 중 하나입니다.

예시:
- 플레이어는 즉시 존재하지만
- 일부 UI / 서브시스템 / 인벤토리 / 맵 오브젝트는 늦게 생성됨
- 저장 데이터는 이미 로드됐지만
- 해당 기여자는 아직 `SaveRegistry`에 등록되지 않음

이 문제는 파일/직렬화가 아니라 **등록 타이밍 문제**입니다.

---

## 4. 복원 로직이 여러 번 호출되어도 안전한지 확인합니다

Core 저장 구조에서는 지연 등록된 객체에 복원이 다시 들어갈 수 있습니다.
따라서 복원 코드는 한 번만 호출된다고 가정하면 쉽게 깨집니다.

체크 항목:
- 같은 데이터가 다시 적용되어도 문제가 없는가
- 기존 상태를 중복 추가하지 않는가
- 컬렉션을 누적해서 두 번 넣지 않는가
- 이전 참조를 안전하게 정리하는가

즉, 복원 코드는 **idempotent** 해야 합니다.

---

## 5. 파생 상태와 원본 상태를 구분해서 저장하는지 확인합니다

저장/복원 버그의 구조적 원인은 종종 여기서 나옵니다.

예시:
- max 에서 계산 가능한 current 를 중복 저장
- 장비/패시브/버프 재계산 결과까지 그대로 저장
- 캐시값과 원본 상태를 함께 저장해서 충돌

이렇게 되면 규칙 변경 후 이전 세이브와 충돌하기 쉽습니다.
가능하면 **원본 상태를 저장하고 파생 상태는 재계산**하는 편이 안전합니다.

---

## 6. 복원 후 후속 동기화 책임이 있는지 확인합니다

저장 복원은 끝났지만,
그 이후 실제 시스템이 다시 계산하거나 UI를 갱신해야 하는 경우가 많습니다.

체크 항목:
- 복원 후 재계산 메서드가 필요한가
- 복원 후 상태 변경 이벤트를 발행하는가
- UI / Presenter 가 그 이벤트를 받는가
- 패시브, 장비, 설정 값 재적용 단계가 필요한가

즉, 복원 성공과 표시 성공은 같은 문제가 아닙니다.

---

## 7. 하위 호환과 기본값을 점검합니다

세이브 포맷은 시간이 지나며 변합니다.
이때 예전 세이브가 깨지는 문제는 보통 다음에서 발생합니다.

- 새 필드 기본값 부재
- null 대응 누락
- enum / key 이름 변경
- 컬렉션 길이 가정
- 버전별 마이그레이션 누락

따라서 “이번 빌드에서는 된다”만 보면 안 되고,
이전 세이브도 읽을 수 있는지 봐야 합니다.

---

## 빠른 체크리스트

- 저장 파일에 실제 값이 기록되었는가
- 저장 기여자와 복원 책임 주체가 명확한가
- 늦게 생성되는 객체의 등록 타이밍을 확인했는가
- 복원 로직이 여러 번 호출되어도 안전한가
- 원본 상태와 파생 상태를 구분해서 저장하는가
- 복원 후 재계산 / 이벤트 / UI sync 가 필요한가
- 기본값 / 하위 호환 정책이 있는가

---

## 자주 생기는 문제

### 1. 파일에는 값이 있는데 게임에서는 기본값처럼 보임

복원 로직이 안 타거나, 복원 후 후속 sync 가 빠진 경우가 많습니다.

### 2. 씬에 바로 있는 객체는 복원되는데 나중에 생긴 객체는 안 됨

`SaveRegistry` 등록 시점을 확인해야 합니다.
지연 등록 객체 복원을 고려하지 않은 구조일 가능성이 큽니다.

### 3. 로드 후 값이 두 배가 됨

복원 로직이 누적형인데 재진입에 안전하지 않은 경우입니다.

### 4. 예전 세이브를 읽으면 일부만 깨짐

새 필드 추가 이후 기본값 또는 마이그레이션 정책이 빠진 경우가 많습니다.

---

## 한 줄 정리

저장/복원 디버깅은 “파일이 있느냐”보다 **누가 저장했고, 언제 등록되었고, 어떻게 다시 적용되었는가**를 기준으로 보는 것이 가장 정확합니다.
